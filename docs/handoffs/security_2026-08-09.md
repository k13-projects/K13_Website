# K13 Website — Security Audit
**Date:** 2026-08-09 · **Auditor:** Irina (Security Auditor) · **Scope:** `/Users/k13/Desktop/PROJECTS/K13_Website`

## What this project actually is
A static, single-file marketing/portfolio site (`index.html`, 831 lines, inline CSS/JS), no build step, no
backend, no server-side code, no database, no auth, no cookies set by the site itself. Per `README.md` it is
hosted on **Vercel** as a static import (`main` = production, feature branches = preview subdomains). This
audit is scoped accordingly — **cloud/database/RLS/webhook findings do not apply here and are out of
scope**, as instructed. What *does* apply to a static site: third-party resource integrity, the one
client-side "form," link hygiene, injection sinks in the inline JS, secrets hygiene, and the security
headers a static host should be told to send.

## Findings (severity-ranked)

| 1 | **Medium** | No security headers configured anywhere in the repo — no CSP, no `X-Frame-Options`/`frame-ancestors`, no `Referrer-Policy`, no explicit HSTS. There is no `vercel.json`, so whatever Vercel sends by default is whatever ships; it isn't guaranteed and isn't verifiable from this repo. For a site with zero user-generated content the risk is mainly clickjacking (no framing protection) and no defense-in-depth against any future injection. | Whole site (deploy config) | Add a `vercel.json` (or Vercel dashboard headers) setting `Content-Security-Policy` (allow-list `fonts.googleapis.com`, `fonts.gstatic.com`, `cdn.jsdelivr.net`, `'self'`), `X-Frame-Options: DENY` (or CSP `frame-ancestors 'none'`), `Referrer-Policy: strict-origin-when-cross-origin`, `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`, `X-Content-Type-Options: nosniff`. |
| 2 | **Low** | The one third-party `<script>` — `https://cdn.jsdelivr.net/npm/lenis@1.1.18/dist/lenis.min.js` (line 635) — is version-pinned but has no Subresource Integrity hash and no `crossorigin` attribute. If jsdelivr were ever compromised or the pinned file mutated, the site would load and run it unverified. | `index.html:635` | Add `integrity="sha384-…"` (jsdelivr publishes hashes) and `crossorigin="anonymous"`. Google Fonts links (lines 8–10) don't support SRI (dynamic CSS) — that's normal, not a finding. |
| 3 | **Low** | The contact "stepper" builds DOM nodes with raw `innerHTML` using user-typed values: `c.innerHTML="<b>"+p[0]+"</b>"+p[1]` where `p[1]` can be the visitor's own name or email, unescaped (`index.html:801`, fed by `sum.innerHTML=""` at line 797). Still worth closing as free defense-in-depth. | `index.html:797,801` | Build the chip with `textContent` (`c.textContent = p[0]; ...` via a child span) instead of `innerHTML`, or run the values through a small HTML-escape helper before interpolating. |

## What was checked and is clean (Pass)
- **No inline event handlers** (`onclick=`, `onerror=`, etc.) anywhere in `index.html` — confirmed by grep, zero matches.
- **No `eval`, no `document.write`, no other `innerHTML`/`outerHTML` sink** besides the one noted in finding 3.
- **No mixed content** — every external resource (fonts, jsdelivr CDN, all 10 portfolio links) is `https://`; zero `http://` references.
- **No real form/endpoint** — the "multi-step contact" flow (lines 783–827) never POSTs anywhere. It collects `type`/`name`/`email`/`why` in a local JS object and, on submit, builds a `mailto:` link with `encodeURIComponent` (properly escaped for URL context) and hands it to `window.location.href`. No network request is ever made by the site; the visitor's own mail client sends it, if they choose to hit send. This eliminates the entire class of server-side input-validation/injection findings a normal contact form would carry.
- **No secrets, keys, or tokens anywhere in the repo or its full git history.** Read all four `scripts/*.sh` (git identity/branch/ship helpers) — pure git plumbing, no credentials, no API calls. Ran `git log --all -p` grepped for `api[_-]?key|secret|token|password|AKIA|sk-[a-zA-Z0-9]{10}|-----BEGIN` across every commit on every branch — zero hits.
- **Personal contact info in the HTML (`projects.k13@gmail.com`, `+1 949 306 6998`) is intentional public business contact info for a portfolio site, not a leak.**
- **`.gitignore` is adequate for what this repo actually is** (`.DS_Store`, `node_modules/`, `*.log`, `.gstack/`, `.claude/`) — there's no build output, no env file, and no backend secret to protect, so there's nothing missing from it that matters.
- One untracked, uncommitted 1.9 MB `Kazim Image.png` sits in the working directory (not in `git ls-files`, never pushed) — not a repo risk, noted only for completeness; no action required unless Kazim wants the stray file cleaned up locally.

## Out of scope (explicitly, per the nature of this project)
No cloud backend, no database, no Supabase/RLS, no auth/session/cookie layer, no webhook, no server-side
code of any kind exists in this repo — none of the standard SaaS-audit categories apply, and padding this
report with them would misrepresent what's actually here. If K13 Website ever grows a backend (e.g., the
contact flow moves from `mailto:` to a real POST endpoint), re-audit at that time — input validation and
endpoint auth would become relevant then, and are not now.

## Bottom line
This is a clean, low-risk static site: no secrets, no mixed content, no working injection path against
anyone but the visitor's own tab, and no data leaves the browser except via the visitor's own mail client.
The only gap worth closing before/soon after next deploy is **security headers at the host level** (finding
1) — a five-minute `vercel.json` addition. Findings 2–5 are nice-to-haves, not blockers. A staff engineer
would approve shipping this as-is and would flag headers + the innerHTML sink as quick follow-ups, not
release blockers.
