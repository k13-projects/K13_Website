state) — not inferred from markup. From page load (stepper untouched, step 1 active):

- **27 focusable stops total, zero invisible-or-inert-but-focused.** The trace runs: skip link →
  brand → 3 nav links → 2 "Start a project" CTAs → "See the work" → feed-toggle → 10 work rows →
  mail/phone links → the **4 visible step-1 `.opt` buttons** → footer email link → focus leaves the
  document. Full JSON trace saved to
  `.../scratchpad/qa_shots_0810/tab_trace.json`.
- Walked the stepper **with the keyboard only** (Enter on the focused `.opt`, fill name, Enter,
  Tab to `emailSkip`, Enter) and re-ran the tab-order scan at each step: at step 1 (name) only
  `nameNext` + the footer link are reachable; at step 3 (why) only `sendIt` + the footer link are
  reachable. `.screen-s[data-s="0"]`, `[data-s="2"]`, `[data-s="3"]` all report `inert === true`
  while inactive; `#stepBack.disabled === true` at step 0 and flips to enabled (not just visible)
  once past it. **The 8 invisible-but-focusable tab stops are gone — confirmed, not assumed.**

## 2. Firing `#sendIt` with empty data — blocked both ways I tried

- **By keyboard from step 1:** covered by the trace above — `#sendIt` is never in the tab order
  until step 3 is reached through the real flow (name + email/skip completed), so there is no
  keyboard path to it with empty data.
- **By forced programmatic bypass** (`document.getElementById('sendIt').click()`, plus a second
  attempt dispatching a raw bubbling `MouseEvent` to rule out `.click()`-specific quirks) — both
  fired **while the stepper sat at step 0 with `data` fully empty**. Neither showed the success
  panel (`#sent.classList.contains('on')` stayed `false` both times).
- **Partial-data adversarial case** (`data.type` set from clicking an `.opt`, `data.name` still
  empty, forced click): also blocked — `sent` never gets `.on`, and the stepper is redirected to
  the name step (`data-s="1"`), matching the `go(!data.type?0:1)` guard logic.
- **Legitimate full flow** (real clicks/keyboard through type → name → skip email → why, then
  `Enter` on `#sendIt`): **succeeds** as designed, `#sent` gets `.on`, confirming the guard isn't
  over-broad and blocking real submissions.

## 4. Keyboard-only pass — three of four clean, **one regression found**

- **Labels:** `#sName`/`#sEmail`/`#sWhy` each resolve `el.labels[0].textContent` to "Your name" /
  "Your email address" / "Why this project matters to you" live in the DOM. Pass.
- **Feed pause control:** reachable in tab order (confirmed in the trace), clicking it flips
  `aria-pressed`/`aria-label`/button text correctly, and it **actually pauses** — held the feed
  text unchanged across 4.2s (longer than the 3.8s rotation interval) while paused, then confirmed
  it changed again within 4.5s of resuming. Pass.
- **`prefers-reduced-motion`:** feed-toggle button itself is `display:none` under reduced motion
  (the whole feed IIFE early-returns on `reduced`, so there's nothing to toggle — consistent, not a
  dead control). `.card` transition duration collapses to `0.001s`, `document.documentElement`
  never gets the `lenis` class, zero console errors. Pass.
- **Skip link — BROKEN.** Tabbing to `.skip-link` and pressing `Enter` (also tested via a direct
  programmatic `.click()`) does **not** move focus to `<main id="main">` and does **not** update
  `location.hash`. Root cause: `index.html`'s pre-existing global smooth-scroll handler
  (`document.querySelectorAll('a[href^="#"]')...addEventListener("click", ...)` around line 667)
  is attached to **every** in-page anchor, including the new skip link. It calls
  `e.preventDefault()` and only does `scrollTo(el)` (Lenis or `scrollIntoView`) — it never calls
  `el.focus()`. That suppresses the browser's native "jump + focus the `tabindex=-1` target"
  behavior that skip links depend on. Proven live: pressed `Tab` (lands on skip link) → `Enter` →
  waited 1.4s for any scroll/Lenis settle → pressed `Tab` again → **focus landed back on the `.brand`
  nav link**, i.e. exactly where a keyboard user would have landed with no skip link at all. The
  skip link is present, visible-on-focus, and correctly `href="#main"`, but it does not functionally
  skip anything for a real keyboard user — the one thing it exists to do. This is a genuine gap in
  item 3 of Natalia's fix ticket ("Landmarks"), not a pre-existing condition she was asked to leave
  alone; the fix needs `el.focus({preventScroll:true})` after the scroll (or excluding
  `.skip-link` from the generic anchor-hijack handler) to actually move focus.

## Verdict

**Not a clean PASS.** The bug this re-run exists to catch — invisible-but-focusable stepper tab
stops and an empty-data `#sendIt` — is **fully closed and proven closed**, three independent ways
(keyboard trace, forced `.click()`, forced `MouseEvent` dispatch), with the false-success copy also
genuinely fixed. That is the headline result and it's solid. But this pass found a **new, real
regression in one of the same ticket's items**: the newly-added skip link doesn't move focus, so it
doesn't functionally work for a keyboard user — the exact class of bug this whole re-run exists to
catch, just in a different control. I'm not rubber-stamping it. Recommending a one-line fix
(`el.focus({preventScroll:true})` after `scrollTo`, or exclude `.skip-link` from the generic anchor
handler) and a fast re-check, not a full pipeline restart — everything else in this pass is clean.
