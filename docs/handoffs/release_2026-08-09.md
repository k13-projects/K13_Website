# K13 Website — Release Readiness Assessment

**Date:** 2026-08-09 · **Assessed by:** Kate (Release Engineer) · **Scope:** assess-only, no shipping.
No branch created, nothing committed, nothing pushed, no PR opened. Read-only git inspection plus
live HTTP checks against the deployed site. Only new file: this handoff.

## 1. Does the release machinery match K13 house rules?

Read `scripts/hm.sh`, `scripts/new-branch.sh`, `scripts/ship.sh`, `scripts/setup-identity.sh` against
`starter-kit/HAIL_MARY.md` and `starter-kit/CONVENTIONS.md` in the War Room repo.

**The scripts themselves are correct.**
- `new-branch.sh` builds `<shortcode>_<monDD>_v<N>` exactly per house spec (lowercases the repo dir
  name for the shortcode by default, finds the next `_v<N>` by scanning existing branches).
- `hm.sh --here` (hm-1) skips branch creation and commits on the current branch, as specified.
- `hm.sh --ship` (hm++) runs `gh pr create --fill` then `gh pr merge <num> --merge` — a real merge,
  **no squash, no rebase, no `--delete-branch`** (branch is kept). This matches house rule exactly.
- Plain `hm.sh` (no flags) stops after `git push -u origin HEAD`, matching "hail mary stops after push."

**One real gap: nothing stops `hm-1` from running on `main`.** `hm.sh` never checks the current
branch before committing in `--here` mode — it trusts the caller. The house rule ("never a direct
main commit") is enforced by discipline/prompt only, not by the tooling. I checked whether GitHub
branch protection backstops this:

```
gh api repos/k13-projects/K13_Website/branches/main/protection
→ 404 "Branch not protected"
```

**`main` is not protected on GitHub.** Nothing technical — not the script, not GitHub — would stop
a direct push to `main` today. This is a latent risk, not an active incident (no evidence it has
happened: `main`'s history is 100% merge commits from PRs, see `git log --oneline`).

**Second gap: the release scripts are not in git at all.** `git log --all --oneline -- scripts/`
returns nothing — `scripts/` has never been committed, on any branch, ever. It exists only on this
machine's disk. A fresh clone of this repo has no `hm.sh`/`ship.sh`/`new-branch.sh` — the very
tooling that's supposed to enforce the ritual isn't backed up by the ritual itself.

## Bottom line

The site is **genuinely live and working** — that's the one thing that matters most and it's solid:
correct content served from Vercel, matches the repo, no downtime. The **git ritual tooling is
correctly built** (hm.sh/ship.sh/new-branch.sh faithfully implement the house branch→PR→merge rules)
but has two soft spots — no branch-protection backstop on GitHub, and the scripts enforcing the
ritual aren't themselves version-controlled. The **P5 polish gate fails on 6 of 8 items** — this is
a working site, not yet a "done" site by K13's own checklist. None of the P5 gaps are urgent/security
(the one Medium item, headers, is already tracked by today's security audit); they're the kind of
thing that's fine to ship past once and circle back to, not a reason to block the current deploy.

**Rollback note** (for the record, though nothing is being deployed today): the current production
deploy is `main` @ `8b3cbc8` (merge of `site13_jul03_v4`). If a future deploy regresses, Vercel's
dashboard keeps every prior deployment as an instant-rollback target (`main`'s deploy history), so
rollback is a dashboard click, not a git revert — no action needed from this pass.
